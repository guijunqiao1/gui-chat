### 模拟练习（不能作为真实成果陈述）

> 假设需求是让客户在 AI 生成过程中实时看到消息和工具状态。我会把 WebSocket 事件约定为 `message_delta`、`message_done`、`error` 和 `heartbeat`，用 Zustand 保存连接状态、当前会话和消息数组。收到增量事件后只追加对应 messageId 的内容，断线时显示可重试状态而不是直接丢失消息；Markdown 使用 react-markdown 渲染，并限制自定义组件只处理受信任的代码块类型。
>
> 结果不会空口说“体验提升”，而会用网络断开、连续发送、超长回复、重复事件等用例验收；如果有埋点，再看连接失败率、首条消息可见时间和用户中断率。

### 高频追问

**问：为什么用 Zustand？**

> 仅在你确实这样使用时回答：对话状态被输入框、消息列表、侧边栏和连接层共同消费，用 Context 容易产生较大重渲染范围；Zustand 可以按 selector 订阅，API 也较轻。复杂异步编排仍放在 service 层，store 只负责状态和简单 mutation。

**问：WebSocket 断线如何恢复？**

> 先说明真实实现。如果没有自动重连，就诚实说“当前由用户重试，后续计划加入指数退避和最大重试次数”。如果已实现，则说明重连次数、退避策略、心跳、重复消息去重和会话恢复依据，不能只说“自动重连”。

**问：如何处理模型返回的恶意 Markdown/HTML？**

> 不能仅回答“react-markdown 很安全”。要说明是否禁用了 raw HTML，是否限制链接协议、图片来源和自定义组件；若没有完成，直接说这是待补的安全项。

### 可用于真实面试的回答模板

> 首页的主要问题是【Lighthouse / RUM 显示的真实症状】，其中 LCP 元素是【元素】。我先在【浏览器版本、设备、网络/CPU 限速、测试次数】下建立优化前基线，而不是先改代码。
>
> 分析后发现瓶颈主要来自【首屏图片体积、阻塞 CSS/JS、第三方脚本、字体、未拆包等真实原因】。对应地，我使用【图片压缩/响应式图片/懒加载/代码分割/Webpack 分析】；首屏资源要优先加载，非首屏资源才使用懒加载，避免为了“懒加载”误伤 LCP。
>
> 优化后我用同一套环境重复跑【次数】次，取【中位数/P75】。LCP 从【真实基线】变为【真实结果】，同时检查 CLS、INP/TBT 和功能回归，确保不是通过隐藏 LCP 元素得到的虚假优化。

### 模拟练习（不能作为真实成果陈述）

> 假设 Lighthouse 显示 LCP 是首屏 Banner，且网络 waterfall 发现图片 1.8MB、为 PNG、没有尺寸信息。我会先转为 AVIF/WebP 并生成响应式尺寸，使用 `preload` 或框架的 priority 让真正的 LCP 图优先请求；导航下方的图片区块改为 lazy loading。然后用 Webpack Bundle Analyzer 找到首页同步引入的图表或编辑器，拆成动态 import，并延后第三方统计脚本。
>
> 我会在固定的移动端模拟、Fast 4G、4× CPU 下至少跑 5 次 Lighthouse，记录 LCP 的中位数、P75、CLS 和 JS transfer。如果由 3.2 秒到 0.96 秒来自生产 RUM，则必须写清是哪个分位数、哪段日期；如果只是本地一次跑分，不能以此作为简历结论。

### 高频追问

**问：LCP 是什么？不是首屏加载完成吗？**

> LCP 是视口内最大内容元素完成渲染的时间，常见是 Hero 图片或大标题。它不是页面所有资源加载完的时间，所以优化时要先找浏览器认定的 LCP element，再针对它的下载、解码、渲染阻塞链路处理。

**问：懒加载为什么可能让 LCP 变差？**

> 如果把真正的首屏 LCP 图也标记为 lazy，浏览器会延后请求它，LCP 反而变差。正确做法是优先加载关键资源、延迟非关键资源；性能优化的核心是资源优先级，而不只是“资源越晚加载越好”。

**问：如何证明 0.96 秒可信？**

> 给出测试条件、报告链接或截图、运行次数和统计口径。如果没有 RUM，只能说“实验室环境中中位数”；生产体验还要用 web-vitals/RUM 看真实用户的 P75。

### 可用于真实面试的回答模板

> 业务希望了解用户从哪个页面进入、如何使用核心功能，以及线上异常和性能问题。我的工作是负责【SDK / 页面集成 / 事件设计 / 上报接口中的实际部分】。
>
> 设计时我把事件分为公共上下文和业务 payload。公共上下文包含【真实字段】，业务事件只允许携带经过定义的字段；这样后端分析能按会话、版本或页面聚合，同时避免各页面随意上报不一致的数据。上报侧采用【真实方案】，并考虑页面卸载、网络失败、重复上报和采样问题。
>
> 我通过【日志、测试环境事件查询、后端验收面板】验证事件到达率和字段正确性，最终支持【真实的分析或排障场景】。如果涉及用户标识或输入内容，我会说明采取了【脱敏/不采集/授权】策略。

### 模拟练习（不能作为真实成果陈述）

> 假设要从零设计前端埋点，我会定义统一事件模型：`eventName`、`timestamp`、`sessionId`、`pageUrl`、`appVersion`、`context`、`payload`。SDK 在页面加载时采集 Web Vitals，在路由变化时发 PV，在关键 CTA 点击时发业务事件，在 `window.onerror` 和 unhandledrejection 中采集错误摘要。
>
> 为避免每次点击都发一个请求，我会做内存队列：达到数量阈值或定时批量 flush；页面 visibilitychange/pagehide 时优先使用 `navigator.sendBeacon`，失败时可选 localStorage/IndexedDB 暂存并在下次启动重试。敏感字段例如手机号、完整输入文本、token 不进入 payload；用户 ID 用内部匿名 ID 或哈希化标识，并遵守公司隐私政策。

### 高频追问

**问：为什么用 sendBeacon？**

> 它适合页面即将卸载时尽力发送少量分析数据，不会阻塞导航。但有 body 大小和接口能力限制，因此日常批量上报仍可能使用 fetch；两者按场景组合，不能说 sendBeacon 能解决全部上报问题。

**问：如何避免埋点影响性能？**

> 事件处理不能在点击主路径做重计算；序列化和上报放在队列批处理，使用采样控制高频事件，SDK 失败不能影响业务。还要测量 SDK 的包体、初始化耗时、请求量及主线程长任务。

**问：如何保证数据可信？**

> 前端数据天然可能丢失、重复或被拦截，因此要加 eventId 去重、版本字段、schema 校验、服务端时间戳和缺失率监控；关键交易数据以服务端事实为准，前端行为数据用于体验分析和辅助诊断。

### 模拟练习（不能作为真实成果陈述）

> 假设客户要求同一产品增加品牌主题、指定入口和企业 SSO。我会把主题、功能开关和 API base URL 通过环境变量或运行时配置注入，避免复制一套代码。Docker 使用多阶段构建：Node 阶段安装依赖并产出静态文件，Nginx 阶段只保留构建产物和配置；Nginx 配置缓存策略，HTML 不强缓存，带 hash 的静态资源长缓存，并将 `/api` 反向代理到后端。
>
> 发布采用带版本号的镜像，先在预发环境执行 smoke test（登录、关键页面、接口、静态资源），再切流。回滚不重新构建，而是回退到上一个已验证镜像。结果应记录为实际交付数量、上线成功率或故障恢复时间，而不是模糊地说“顺利上线”。

### 高频追问

**问：Docker 给前端部署带来的价值是什么？**

> 前端静态站点不是必须 Docker 化，但 Docker 能固定 Node 构建环境、依赖版本和 Nginx 运行配置，降低“本地可构建、服务器失败”的差异，也方便交付客户私有环境。代价是镜像构建、漏洞扫描和配置管理也要规范。

**问：Nginx 如何处理静态资源缓存？**

> 通常 HTML 配置短缓存或不缓存，以便快速拿到新入口；文件名带 content hash 的 JS/CSS/图片可以长缓存并 immutable。部署后必须验证资源路径和缓存命中，避免 HTML 已更新但客户端继续加载旧 chunk 导致白屏。

**问：定制需求如何避免污染主产品？**

> 优先抽象稳定的配置和扩展点，使用 feature flag/tenant config，而不是在业务代码到处写客户名判断。确实不可复用的部分可以隔离适配层；每个客户配置有独立验收用例，避免影响默认租户。
