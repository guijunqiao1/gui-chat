## 0. 先用这一段介绍项目（30～45 秒）

> 我做的是一个基于 TypeScript 和 Next.js 的全栈 AI Chat 应用。用户可以流式对话，并按需调用联网搜索、图片生成、知识库检索和跨会话记忆检索；同时提供文件上传、语音输入输出、会话管理、分享和 OAuth 登录。前端重点解决了流式高频更新、工具调用多阶段状态一致性和长列表渲染的问题；后端用 Prisma + PostgreSQL 管理用户与会话，并把工具调用封装为可组合的函数定义。最近我把 RAG 分为知识库检索和历史记忆检索两条链路，并用请求级工具工厂保证多用户隔离。

### 推荐回答结构

每个亮点按 **问题 → 决策 → 实现 → 结果 → 边界** 回答：

1. **问题**：真实的用户体验或工程约束，而不是“我用了某技术”。
2. **决策**：说清为什么选它，以及为什么不选一个常见替代方案。
3. **实现**：点出关键数据结构、事件、接口或 SQL，展示亲自做过。
4. **结果**：只报可复现的指标；没有测量就说“设计目标/待测指标”。
5. **边界**：主动说明失败处理、规模上限或下一步优化，体现工程判断。

## 1. Fetch + ReadableStream 解析 SSE

**简历表述（可用）**

> 针对原生 `EventSource` 仅支持 GET、不能携带请求体和自定义鉴权头的限制，使用 `fetch` 发起 POST 请求，并消费 `Response.body` 的 `ReadableStream`；封装增量 UTF-8 解码、跨 chunk buffer 和 SSE 行解析，支撑带模型配置、附件和工具开关的流式对话。

### 30 秒模板

> 聊天请求需要以 POST 传递用户输入、模型配置、附件和工具开关，而 EventSource 的能力不足。因此我用 fetch 拿到响应流，通过 `TextDecoder` 的 stream 模式把字节流转为文本，并保留未结束行到下一次读取后再解析。这样既保留 SSE 的实时性，也能正常携带 JSON body 和 Cookie 鉴权。

### 追问：为什么不能直接用 WebSocket？

> 这是服务端模型供应商返回的单向 SSE 流；客户端主要是发送一次请求、持续接收 token。fetch 流的实现和 HTTP/鉴权/代理体系兼容成本更低。若要做协作编辑、服务端主动推送或双向实时控制，再评估 WebSocket。

### 追问：chunk 恰好把一个 JSON 或汉字切开怎么办？

> UTF-8 解码时开启 `stream: true`，由 TextDecoder 保留不完整字符；随后按行分割 SSE 数据。最后一行不完整时不解析，把它放回 `remaining buffer`，等待下一次 chunk 拼接。流结束时再做一次尾部 flush。

### 追问：如何处理断开、错误和取消？

> 请求由 AbortController 管理；读取异常会转为错误 SSE 状态并刷新尚未渲染的 buffer。正常 `complete` 事件也会强制 flush，避免最后一帧 token 丢失。生产环境还应按错误类型区分网络失败、上游限流和用户主动取消。

## 2. 消息有限状态机（FSM）与多轮 Function Calling

**简历表述（可用，建议写明完整状态）**

> 以消息为粒度设计有限状态机（`idle / thinking / tool_calling / answering / error`），由 SSE 事件驱动转移；同时维护工具调用 ID、进度和结果，解决多轮 Function Calling 下“正文在流式输出、工具卡片状态却滞后”的一致性问题。

### 30 秒模板

> Function Calling 不是单段文本流，而是“思考、调用工具、等待结果、继续回答”的循环。如果只用一个 `isLoading`，工具结束和下一轮文本开始时 UI 很容易乱。我的做法是每条 assistant 消息维护独立状态机，SSE 的 `thinking`、`tool_call`、`tool_progress`、`tool_result`、`answer` 和 `complete` 映射为事件；非法转移直接拒绝。工具实例按 toolCallId 存储，所以多个工具并行时也能分别显示状态。

### 可展开的技术细节

- `VALID_TRANSITIONS` 把允许的转移显式声明，例如 `thinking → tool_calling → answering → idle`。
- `TOOL_PROGRESS / TOOL_COMPLETE / TOOL_CANCEL` 不粗暴改变阶段，而是更新 `activeTools` 中对应的调用记录。
- 状态按 `messageId` 存在 `Map` 中，不把瞬态运行态混入需要持久化的消息正文。
- 服务端最多执行有限轮工具调用，避免模型反复调用造成无限循环。

### 追问：模型先输出文本又发工具调用，怎么处理？

> 客户端把该轮临时文本与 tool calls 一并保留；服务端获得工具结果后，把 assistant tool-call 消息和 tool result 消息追加到上下文，再发起下一轮模型调用。最终用户看到的是同一条 assistant 消息的连续生命周期，而不是多条彼此脱节的消息。

### 追问：为什么状态机不放在后端？

> 后端负责工具执行和消息持久化，前端负责交互展示。前端状态机的目标是把网络事件稳定地映射为 UI；服务端同样有轮次上限和工具调用编排，两者职责不同但事件协议一致。

- `features/chat/utils/message-state-machine.ts`
- `features/chat/types/message-state.ts`
- `features/chat/store/chat.store.ts`
- `features/chat/services/chat.service.ts`

## 3. rAF 流式缓冲，控制高频渲染

**简历表述（当前代码支持；数字需重新测量）**

> 使用 buffer 队列聚合高频 token，并以 `requestAnimationFrame` 一帧一次批量提交 Zustand 更新；流结束和错误时强制 flush，在保证最后 token 不丢失的前提下将 UI 更新上限约束为屏幕刷新频率。

### 30 秒模板

> 上游可能在很短时间内推送很多 token。如果每个 chunk 都 setState，React 会反复协调 Markdown 和长消息列表。于是我把 thinking 和 answer 分成两个 StreamBuffer：chunk 先追加到字符串 buffer，同一帧只调度一次 rAF；回调中再一次性 append 到 store。结束、报错和取消时 forceFlush，保证尾部内容可见。

### 追问：为什么分 thinking 和 answer 两个 buffer？

> 它们属于不同展示区域和状态阶段。如果混在一个 buffer，会在状态切换时混淆内容，也不能分别控制 UI。拆分后状态机和渲染区域是一一对应的。

### 追问：这会增加首 token 延迟吗？

> 最多增加一帧，通常约 16.7ms（取决于屏幕刷新率）；相较于避免每 token 触发重渲染，这个取舍更合理。应通过首 token 时间、帧率和 React Profiler 验证，而不是凭感觉。

### 数字使用规范

当前代码注释写的是“80～120 次/秒收敛至 ≤60 次/秒”，它只能证明设计意图，**不能证明“降到 40 次/秒以下”**。只有在固定模型、网络、消息长度和设备条件下录制 Performance/Profiler 后，才可以写：

> 在【设备/浏览器/测试文本】下，setState 提交峰值由 X 次/秒降至 Y 次/秒。

### 代码锚点

- `features/chat/utils/stream-buffer.ts`
- `features/chat/services/chat.service.ts`

## 4. 长消息与 Markdown 布局稳定性

**当前结论：需要降级表述。**

当前项目确有未闭合 JSON/Markdown 的补全处理，也有虚拟列表的高度预估；但未检索到 `overflow-anchor` 配置，也没有统一的“流式块预留骨架高度”实现。

### 诚实的替代说法

> 针对流式期间不完整的结构化内容，在 Markdown 渲染前做闭合补全，并在虚拟列表中为普通文本、思考内容和代码块给出不同的预估高度，降低内容逐步完整时的视觉跳动；后续计划补充滚动锚定与基于实际测量的动态高度校正。

### 追问：为什么不直接写 `min-height`？

> 固定 min-height 会给短消息留下空白、给长代码块仍不够用。更稳妥的是基于内容类型给合理 estimate，渲染后测量实际高度并通知 virtualizer 校正；对正在流式的最后一条消息再保持底部跟随策略。

### 不建议使用的原表述

> “组合预留骨架高度、overflow-anchor 滚动锚定、未闭合 Markdown 块自动补全消除抖动。”

除非先补齐前两项实现并用 CLS/录屏证明，否则这句话会被追问到实现细节时失分。

## 5. TanStack Virtual + 游标分页

**简历表述（可用）**

> 基于 TanStack Virtual 只渲染可视区及 overscan 消息，结合以消息 ID 为游标的分页接口加载历史记录；针对流式消息按内容类型给出初始高度估计，并在新增消息时维护底部跟随与用户上滑阅读的行为。

### 30 秒模板

> 长会话如果完整渲染，会让 Markdown、代码高亮和图片节点持续增加。消息列表使用 `useVirtualizer`，只保留视窗附近的元素；后端分页不是 offset，而是带 cursor 的消息 ID，因为新增消息不会导致前面的 offset 漂移。流式中的最后一条高度不断变化，因此我设置了按内容类型区分的 estimate，并在用户未主动上滑时保持贴底。

### 追问：为什么 cursor 比 offset 好？

> offset 在有新消息插入或删除时可能重复、漏数据，而且越往后数据库跳过的行越多。cursor 用稳定排序字段（这里围绕消息时间和 ID）定位下一页，数据变化下结果更可靠。

### 追问：动态高度会不会造成滚动跳动？

> 会，所以 estimate 只是降低初始误差，不能假装精确。下一步会接入 `measureElement` 或在 Markdown/图片完成渲染后调用 virtualizer 的测量更新，并在用户正在阅读历史消息时禁止自动贴底。

### 代码锚点

- `features/chat/components/MessageList/index.tsx`
- `app/api/conversations/[id]/messages/route.ts`
- `server/repositories/message.repository.ts`

## 6. RSC 分享页与性能指标

**当前结论：架构表述可用，具体指标不可直接写。**

分享页是服务端 page，服务端调用 Markdown 渲染工具后将 HTML 交给客户端展示，这一架构成立。但当前仓库没有可审计的“Page chunk 5.6KB、TBT 90ms”基线、构建报告或 Lighthouse 报告。

### 可用回答

> 对公开分享页，我把 Markdown 到 HTML 的转换前移到服务端，减少客户端首次渲染时的解析和高亮工作；性能是否改善通过 Next build 的产物分析、Lighthouse 的 TBT/LCP 和真实页面数据共同验证，而不是只看某次本地结果。

### 追问：服务端渲染有什么代价？

> 服务器 CPU 增加，缓存策略要设计好；而且服务端生成 HTML 必须严格消毒，否则安全风险比客户端更高。适合只读、公开、首屏体验优先的分享页，不适合高度交互且频繁局部更新的聊天主界面。

### 指标补证清单

1. `next build` 后保存 bundle analyzer 截图与版本号。
2. 用无痕 Chrome、固定网络/CPU throttle 连续跑至少 3 次 Lighthouse。
3. 记录页面 URL、设备、日期、median TBT/LCP/JS transfer。
4. 在简历中写条件，例如“在移动端模拟 4× CPU 下，TBT P50 为 90ms”。

## 7. OAuth 弹窗与跨窗口通信

**简历表述（可用）**

> 设计 OAuth 弹窗登录：主窗口通过 `window.open` 发起认证，回调页使用 `postMessage` 通知成功或取消，并以 session 轮询作为兜底；验证 `event.origin` 后刷新主窗口会话，避免全页跳转打断当前对话上下文。

### 30 秒模板

> 聊天输入区里用户可能已有未发送内容或正在浏览会话，如果 OAuth 用全页跳转，恢复体验较差。因此我在主窗口打开受控尺寸的认证弹窗，成功回调页向 opener 发送事件；主窗口严格校验 origin 后刷新 session。考虑 postMessage 可能丢失或用户手动关闭弹窗，还加了关闭检测和 session 轮询兜底。

### 追问：postMessage 的安全要点？

> 发送时 targetOrigin 不能写 `*`，接收时必须检查 `event.origin`，必要时还要校验 event.source 是否是创建的 popup，并限制 message 的 type/schema。认证本身仍依赖 OAuth 的 state、PKCE 和服务端 callback 校验，postMessage 只负责通知 UI。

### 代码锚点

- `features/auth/hooks/use-oauth-popup.ts`

## 8. 鉴权与 XSS：必须如实回答

**当前 JWT + HttpOnly Cookie 表述可用：**

> 用户登录后由服务端签发 JWT，存入 `HttpOnly`、`SameSite=Lax` Cookie；脚本无法直接读取 Cookie，从而降低令牌被 XSS 窃取的风险。生产环境开启 `Secure`，服务端从 Cookie 校验并解析用户身份。

### 必须更正的简历表述

**不要说“已配置 `rehype-sanitize` 白名单过滤”。** 当前代码：

- 客户端 Markdown 使用 `rehype-raw`；
- 服务端 Markdown 渲染使用 `remark-html`，并显式设置 `sanitize: false`；
- 依赖中也没有 `rehype-sanitize`。

这意味着不可信的 AI 输出或分享内容可能构成 XSS 风险，不能作为“已完成的安全能力”写在简历里。

### 被问到时的正确回答

> 我识别到 AI 输出属于不可信输入。当前分享页为了支持自定义块使用了原始 HTML，现状存在 XSS 风险；正式上线前应默认禁用 raw HTML，或接入 `rehype-sanitize` 并维护白名单，只放行必要标签、属性和 URL 协议，同时对自定义 image/weather/chart 块先进行 JSON schema 校验和输出转义。

### 追问：HttpOnly 是否“防 XSS”？

> 它只防止 JavaScript 直接读出 Cookie，不会阻止被注入脚本以当前用户身份发起请求，因此不能替代输出消毒、CSP、CSRF 策略和安全的 DOM API。

### 建议的安全改造（完成后才能写入简历）

1. 安装并启用 `rehype-sanitize`，从严格默认 schema 开始扩展。
2. 不允许 AI 输出任意 HTML；自定义块走 JSON schema 而非 `rehype-raw`。
3. 为分享页配置 CSP，限制 script、img、frame 来源。
4. 对 Cookie 鉴权的写操作评估 CSRF token 或严格 Origin 校验。

### 代码锚点

- `app/api/auth/login/route.ts`
- `server/auth/jwt.ts`
- `features/chat/components/MessageContent/index.tsx`
- `server/utils/markdown.ts`

## 9. 双场景 RAG 与请求级工具工厂

**简历表述（可用，但先确认已完成数据写入与迁移部署）**

> 为对话系统接入双场景 RAG：文档知识库使用 pgvector 和参数化 raw SQL 在 PostgreSQL 中完成余弦近邻排序；跨会话记忆将 embedding 以 JSON 存储，在应用层计算余弦相似度并叠加重要度和时间衰减。两类工具通过 per-request 工厂携带 `userId` 和请求 API key，保证多用户检索隔离并避免全局工具注册表产生用户上下文串用。

### 30 秒模板

> 我把 RAG 按数据规模和访问模式拆成两类。知识库 chunk 数量可能持续增长，因此把向量放到 pgvector，查询时用 `<=>` 在数据库排序，只取 top K；历史记忆通常规模较小，但需要结合重要度和时间衰减，先限制最多取 500 条到应用层计算，更方便迭代业务分数。关键点是工具不能全局注册成带 userId 的闭包，否则并发请求可能串数据，所以每个 chat 请求创建自己的 knowledge_search 和 memory_search 实例。

### 追问：为什么不全部用 pgvector？

> 长期看可以统一。但记忆检索不仅是语义相似度，还有 importance、recency、排除当前会话等业务权重。现阶段记忆量受限于 500 条，应用层计算实现更快；当每用户记忆规模或 QPS 增大，再把权重公式迁移到 SQL、物化列或专用向量检索系统。

### 追问：raw SQL 会不会有注入风险？

> 向量文本和 userId 都作为 Prisma SQL 参数绑定，不拼接到 SQL 字符串中。向量字面量仅由 embedding API 返回的 number 数组构造，仍应校验维度与有限数值，避免异常数据导致查询失败。

### 追问：如何确保用户 A 搜不到用户 B？

> 知识库 SQL 在 JOIN 后强制 `WHERE document.userId = 当前 userId`；记忆查询也按 `userId` 限制。更重要的是 userId 来自服务端认证上下文，不接受模型函数参数或客户端传入的 userId。

### 追问：RAG 失败怎么办？

> embedding API 配置超时，工具返回结构化错误给模型；没有命中返回明确空结果，提示模型不要把空结果当作事实。生产还应记录检索命中率、工具失败率、延迟、引用覆盖率，并评估阈值过滤与 rerank。

### 追问：如何评估效果？

> 准备标注集：每题的目标文档/记忆和可接受答案。离线看 Recall@K、MRR、上下文相关性；在线看工具调用率、空结果率、答案引用率和人工正确率。不能只以“模型回答看起来不错”作为评价。

### 当前边界与风险

- 知识库向量列固定为 `vector(1024)`，embedding 模型必须保持相同维度；切换模型需要重建索引。
- `ConversationMemory` 的应用层检索有 `take: 500` 上限；规模扩大后需要下推数据库。
- 文档上传、切块、向量化和重试任务必须有完整的异步索引链路；没有这条写入链路，检索工具只会返回空结果。
- “聊天服务改动 < 5%”不建议作为面试核心指标；应改为“保留原全局工具注册表，仅为有用户上下文的工具增加请求级装配”。

## 13. 模拟面试：可直接使用的真实问答

> 以下回答故意比“30 秒模板”更完整，适合一面、技术二面中面试官继续追问的场景。请按自己实际贡献调整第一人称表述；没有亲自实现或验证的细节不要背诵。

### Q1：请详细介绍一下这个项目，以及你负责的部分。

**参考回答（约 90 秒）**

> 这是一个 Next.js 的全栈 AI Chat 应用，核心体验是用户发送一条消息后，前端实时接收模型 token，同时模型可以根据任务调用联网搜索、图片生成和 RAG 检索。应用还支持文件附件、语音输入输出、会话分页、公开分享和 OAuth 登录。
>
> 我重点负责聊天主链路和它的工程稳定性。前端没有直接使用 EventSource，因为聊天需要 POST body 传递模型、开关和附件；我改为 fetch + ReadableStream，自己处理 UTF-8 分片和 SSE 的跨 chunk 拼接。其次，工具调用让一条消息不再只是“生成中或结束”两种状态，所以我按消息建立了 thinking、tool calling、answering 等状态机，toolCallId 贯穿服务端事件和前端卡片。最后针对 token 高频刷新，我用 requestAnimationFrame 把同一帧内的 chunk 合并提交，降低 Markdown 和虚拟列表的重复渲染。
>
> 后端部分使用 Prisma 管理会话和消息。RAG 上我分成文档知识库与跨会话记忆：文档量可能增长，走 PostgreSQL 的 pgvector；记忆需要时间衰减和重要度，当前规模下在应用层计算更容易迭代。两类检索工具都是按请求创建，把当前 userId 封进闭包，避免全局单例工具在并发用户间串上下文。

**面试官继续问：“最大的难点是什么？”**

> 最难的是多轮工具调用的状态一致性。模型可能先输出 reasoning，然后发起一个或多个 tool call，收到 tool result 后再继续回答。早期如果只用一个 loading 状态，正文、工具卡片和停止按钮会不同步。我把网络事件抽象为状态机事件，例如 START_TOOL_CALL、TOOL_PROGRESS、TOOL_COMPLETE，只有合法转换才更新；而且用 toolCallId，而不是工具名称，处理同一个工具并发调用两次的情况。

**可以反问**

> 您们团队在流式 Agent 产品中，通常是让前后端共享状态机协议，还是由前端根据事件做更轻量的状态归约？

### Q2：为什么 EventSource 不满足需求？你的 SSE 解析具体怎么做？

**参考回答**

> 原生 EventSource 适合简单的 GET 订阅，但这个聊天接口需要 POST JSON：里面有用户消息、选中模型、thinking 开关、联网搜索开关和附件；同时鉴权和请求控制也希望走现有 fetch 体系。因此我用 fetch 发起 POST，检查响应状态后取 `response.body.getReader()`。
>
> 读取时不能假设一次 read 就是一个完整 SSE event。网络层可能把一个 UTF-8 汉字切成两段，也可能把一条 `data: {...}` 拆成多个 chunk。所以我用 TextDecoder 的 stream 模式解码，把文本累积在 buffer；每次只解析完整行，最后一条不完整的内容继续保留到下一次。解析出 JSON 后再按 `type` 分发给 thinking、answer、tool_call 等处理器。结束、AbortError 和非 2xx 响应走不同分支，最终都会 flush buffer 并让消息状态退出 streaming。

**追问：“为什么不直接用现成 SSE 库？”**

> 可以用，但这里协议比较轻量，核心风险是边界处理而不是连接管理；自定义实现更容易把工具调用事件、埋点和 AbortController 接在同一条链路里。如果协议发展到重连、Last-Event-ID、订阅复用等场景，我会优先选成熟库或把解析层抽成单独包并补协议测试。

**追问：“如何测试分包？”**

> 单测会构造任意边界切分的字符串，例如把 `data:`、JSON 花括号、中文字符、`\n\n` 分到不同 chunk，断言最终事件序列不变；再测流结束时无换行尾部是否仍会被处理。这个测试比只用真实网络调试更可靠。

---

### Q3：详细说说你的状态机，为什么 Zustand 还需要 FSM？

**参考回答**

> Zustand 解决的是“状态放在哪里、谁能订阅”，不是“状态怎么合法演化”。工具调用场景里，如果没有状态机，很容易出现 answer 已经结束但 tool 卡片还在 loading，或者 tool result 到来后把已经 error 的消息重新改成 streaming。
>
> 因此我把每个 assistant 消息的运行态建模为 `idle / thinking / tool_calling / answering / error`，并维护一个 `VALID_TRANSITIONS` 表。SSE 事件不是直接改 UI，而是先转换成状态机事件。比如 START_THINKING 只能从 idle 进入 thinking，START_TOOL_CALL 可以从 thinking 或 answering 进入 tool_calling，COMPLETE 回到 idle；非法事件直接忽略并记录 warning。工具详情用 `Map<toolCallId, ActiveTool>` 保存，所以可以在同一条消息中显示多个工具的 running、progress、completed 或 failed。
>
> Zustand 负责把这个纯状态机结果提供给组件订阅，业务编排仍放在 ChatService。这样 UI 组件不需要知道 SSE 协议，测试时也可以脱离 React 直接测试状态转移表。

**追问：“你这个 FSM 有什么不足？”**

> 当前 phase 是单值，而工具是集合；多个工具并行时，整体仍停留在 tool_calling，细粒度状态在 activeTools 内表达。这对 UI 足够，但如果未来要支持任务树、人工确认、工具重试或子 Agent，就应把它扩展为显式的 workflow 状态，或使用状态机库，并让服务端和前端共享事件 schema。

**追问：“为什么不用 XState？”**

> 目前状态和事件数量有限，一个纯 TypeScript 转移表更轻、依赖更少，也便于接入现有 Zustand。XState 在可视化、并行状态、层级状态和模型化测试上更成熟；状态复杂度继续增加时值得迁移，但现在手写 FSM 的维护成本更低。

### Q4：rAF 缓冲真的能优化吗？会不会造成内容延迟？

**参考回答**

> 能优化的是 UI 提交频率，不是模型生成速度。上游 token 到达频率可能超过浏览器一帧的渲染能力，如果每个 chunk 都 append 到 store，就会触发大量 React 更新、Markdown 重解析和虚拟列表高度变化。我的 StreamBuffer 先把 chunk 追加到内存字符串，同一帧只注册一次 requestAnimationFrame，下一帧一次性把累计内容提交；thinking 和 answer 分开缓冲，避免阶段内容混杂。
>
> 代价是首个或某个 token 最多等待一帧，一般约 16ms；对流式对话而言，这远小于网络与模型 token 间隔。流结束、报错、用户停止时会 forceFlush，所以不会因等待下一帧丢掉末尾内容。
>
> 我不会在没有测量时承诺“降到 40 次每秒”。正确做法是通过 React Profiler 看 commit 数，Chrome Performance 看主线程和长任务，在固定浏览器、网络和文本长度下对比优化前后中位数。现有实现能把提交上限约束到刷新率附近，但最终数值取决于设备和流速。

**追问：“为什么不用 debounce？”**

> debounce 的时间窗口和屏幕渲染不同步，持续流入时可能推迟更新，结束时也要额外处理尾部；rAF 天然与浏览器绘制节奏对齐，能保证每帧至多一次视觉更新，更适合这种 UI 流式场景。

---

### Q5：长会话的虚拟列表如何兼顾流式内容与滚动体验？

**参考回答**

> 消息列表使用 TanStack Virtual，只渲染视口附近的项目并设置 overscan，避免上百条 Markdown 和代码块同时在 DOM 中。数据侧通过 cursor 取历史消息，而不是 offset；cursor 相对新增消息更稳定，也避免大 offset 的扫描成本。
>
> 难点是最后一条 assistant 消息在流式增长，高度不固定。当前会按用户消息、普通回答、thinking、代码块给不同的 estimate；用户未主动上滑时保持底部跟随，用户上滑阅读历史后停止自动贴底。后续我会用 `measureElement` 或内容块渲染完成后的测量来进一步减少 estimate 和实际高度的差距。

**追问：“为什么新增消息会影响 cursor 分页？”**

> 如果使用 offset，例如请求第 20～40 条，此时新消息插入顶部，原来的第 20 条就变成第 21 条，下一页可能重复或漏数据。cursor 按一个稳定的定位点继续取“它之前”的记录，能更好应对数据变化；排序字段还要考虑相同 createdAt 时用 ID 作为次级排序，保证确定性。

### Q6：讲讲 RAG 的整体设计，为什么有两种方案？

**参考回答**

> 我先按问题来源拆分。用户问“手册里怎么规定”“上传文档写了什么”时，目标是文档知识库；文档通常会切 chunk、数量持续增长，所以由 embedding 检索后，在 PostgreSQL 使用 pgvector 的余弦距离操作符排序，只返回 top K 相关片段和来源。用户问“我之前提过什么偏好”时，目标是跨会话记忆；它当前每用户规模较小，但评分会考虑向量相似度、重要度和时间衰减，因此取出受限数量的数据在应用层计算，迭代业务权重比较直接。
>
> 两者都不是把 userId 暴露给模型。Chat Service 从鉴权上下文拿 userId 和用户实际使用的 API key，然后通过工厂函数创建带闭包的 `knowledge_search` 和 `memory_search`。如果把这种工具注册到全局单例，用户 A 的闭包可能覆盖用户 B，造成严重的越权问题；请求级实例避免了这个问题。

**追问：“raw SQL 如何保证安全和性能？”**

> 安全方面，userId 和向量值都以 Prisma 参数绑定，而不是字符串拼接；向量还应校验是否是有限数值、维度是否等于索引维度。性能方面，对 document chunks 建 HNSW 向量索引，SQL 的 WHERE 先限定 userId，再按向量距离取有限 top K。实际还要压测不同数据量下的 P95，评估 HNSW 参数、过滤条件和 rerank 成本。

**追问：“应用层余弦计算的上限是什么？”**

> 现有实现明确限制最多取 500 条记忆。这个方案适合原型和中小规模，但复杂度是 O(n × d)，每个用户记忆多或并发高时会成为瓶颈。届时我会把记忆也迁移到 pgvector，或先用数据库过滤、再在小候选集上计算时间和重要度重排。

**追问：“怎么防止模型根据无关检索结果胡编？”**

> 工具返回内容和来源，让 prompt 要求优先基于片段回答；空结果应显式告诉模型“未命中”，而不是返回空字符串。进一步可加相似度阈值、reranker、引用标记，以及离线标注集评估 Recall@K 和答案引用正确率。

### Q7：你如何看待当前项目的安全问题？

**参考回答（务必诚实）**

> 鉴权层面，项目的登录 token 放在 HttpOnly Cookie，前端脚本无法直接读 token；生产环境开启 Secure，并使用 SameSite 限制跨站携带。但这只能降低 token 被直接窃取的风险，不能解决 XSS 造成的代操作。
>
> 我审查 Markdown 链路后发现当前客户端使用 rehype-raw，服务端分享页也存在关闭 sanitize 的配置，因此不能声称项目已经完成了 Markdown XSS 防护。这是我会优先修复的风险：默认不信任模型输出，禁用 raw HTML 或引入 rehype-sanitize 的严格白名单；自定义块只接受 schema 校验过的 JSON；再配合 CSP、图片 URL 协议白名单和敏感写操作的 Origin/CSRF 防护。

**追问：“为什么 AI 输出也要当作不可信？”**

> 模型输出可能被 prompt injection 间接影响，也可能回显用户上传内容或外部搜索内容；从浏览器角度它和用户输入一样都是不可信数据。只要最终进入 `dangerouslySetInnerHTML` 或允许 raw HTML，就必须消毒。

---

### Q8：OAuth 弹窗的实现有什么坑？

**参考回答**

> 全页 OAuth 跳转会让聊天页面卸载，用户的输入、滚动位置和流式上下文体验都较差。所以主窗口打开认证 popup，callback 页面完成登录后通过 postMessage 通知 opener，主窗口校验 event.origin 后刷新 session；如果用户关掉弹窗或 postMessage 没到达，就轮询 popup.closed 和 session 作为兜底。
>
> 安全上 postMessage 不能使用 `*` 作为 targetOrigin，接收方要校验 origin、消息类型和最好校验 source 是否为预期弹窗。它只做 UI 通知，不替代 OAuth 的 state/PKCE/callback 校验。还要处理 popup 被浏览器拦截、重复 success、用户取消和 cleanup，避免遗留 interval 或 message listener。

---

### Q9：如果让你继续做这个项目，你会优先做什么？

**参考回答**

> 我会按风险和收益排序。第一是修复 Markdown XSS 链路，因为这是上线安全风险；第二是把文档上传到切块、异步 embedding、重试和删除索引的全链路产品化，并补 RAG 离线评测；第三是把流式协议和状态机做单测与契约测试，覆盖断流、跨 chunk、并行工具和多轮调用；第四再做性能压测与可观测性，把首 token、工具耗时、检索命中率和取消率作为指标。这样能先保证安全与正确性，再优化体验和规模。

**追问：“为什么不先加更多模型/更多工具？”**

> 工具越多，错误面和安全边界越大。先把现有工具的用户隔离、超时、重试、可观测性和 UI 状态做稳，新增能力的边际价值才更高。

## 14. 临场回答技巧

1. 不要一次讲完所有实现。先给结论，等面试官选择追问方向。
2. 数字必须带条件：测试设备、版本、样本和统计口径。没有证据就说“目标”或“待测”。
3. 被问到没实现的点时，不要硬答。使用“当前现状 → 风险 → 已知方案 → 优先级”的结构。
4. 区分“我主导实现”“我参与集成”“我调研过”。真实性比包装更重要。
5. 每个答案最后留一个可追问的钩子，例如“这里还有一个并发隔离的取舍”，让面试官看到深度。
